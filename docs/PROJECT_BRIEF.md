# Project brief

## What it is

ScriptPlayground is a local Discord bot development environment. A developer writes ordinary `discord.py` code, runs it without a Discord token or server, and sees captured messages, embeds, components, modals, commands, and errors in a Discord-like browser UI.

The product goal is not to clone Discord. It is a safe local test bench for bot UI and behavior.

## Setup and verification

Run these commands from the `ScirptPlayground/` project root. The runtime assumes a working Python installation and the dependencies listed in `requirements.txt`; install them once with:

```bash
python -m pip install -r requirements.txt
```

Launch the local UI:

```bash
python -X utf8 main.py --no-browser
```

In another shell, from the same project root, run the checks:

```bash
python -X utf8 -m tests.test_smoke
ruff check .
PYTHONPYCACHEPREFIX=.test-artifacts/pycache python -X utf8 -m compileall -q .
```

The last command keeps generated bytecode under `.test-artifacts/`. Do not run verification from the repository parent or place test logs and caches inside `bots/`.

## Primary workflow

```text
Write bot.py
   ↓
Run locally
   ↓
Mock Discord captures messages and interactions
   ↓
Browser renders the session
   ↓
Act as You/Alice/Bob/Carol
   ↓
Click buttons, use selects, submit modals, invoke commands
   ↓
Inspect the resulting messages and console events
```

## Current capabilities

- Local aiohttp web app with no network connection to Discord.
- Real `discord.py` objects used by user scripts.
- Mock guild, members, roles, channels, messages, interactions, responses, and follow-ups.
- Selectable session user through the **Act as user** control.
- Correct interaction types for application commands, components, and modal submissions.
- Role-derived guild permissions and channel overwrites using `@everyone`, role, and member precedence.
- Administrator bypass and separate user/bot interaction permissions.
- Permission enforcement for the existing send/delete operations, interaction responses, and follow-ups.
- Components V2 design bridge and visual message builder, with fixed bridge round-trip fixtures covering nested components and gallery/separator boundaries.
- Folder-backed `bots/<name>/bot.py` workspaces.
- Vendored Embeder provenance exposed through `GET /api/embeder/info`; the current marker records DiscordEmbeder commit `0fc06253ce5c86ac77a91b4f4dabfcec49b4daf8`.
- Readable permission-denial diagnostics that identify the existing resolution step that rejected an operation.
- A runtime **State inspector** in the console pane showing the active user, bot, channel, counts, users, channels, current permission results, and recent event snapshot.
- **Events** and **Actions** inspector tabs showing structured runtime entries; selecting an entry reveals its details and simulated API operation arguments, including missing, denied, blocked, and unanswered attempts. Expanded details remain visible while the session refreshes.
- Local script library, saved design projects, and mock runtime stress coverage.
- Canonical project-state validation before design loading, saving, code generation, and runtime use.

## Deliberate constraints

- One simulated guild.
- Fixed fixture users and roles.
- Single-file bot workspace execution (`bot.py`).
- No Discord token, gateway, REST calls, or production deployment.
- No full permissions editor, voice transport, multi-guild model, scenario runner, or broad event bus yet.
- No new dependency is needed for the current product.

## What success looks like

A user can answer: “What will my bot send, and what happens when a user interacts with it?” without creating a Discord server or risking a real bot. The feedback loop should stay fast, deterministic, inspectable, and close enough to `discord.py` to make prototypes useful.
